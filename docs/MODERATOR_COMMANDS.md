# Signed in-chat pending review · Group 5B

These commands use the existing signed original-chat broadcaster/moderator identity. They do not grant control sessions, add scopes, call a username resolver, ban a Twitch user or move the relic. Default approval remains manual.

- `!relic pending` returns only a bounded count and instructions. It never publishes pending text, names, token links or private mark metadata. The mark document and private share grants are unchanged.
- `!relic approve last` approves the latest **eligible pending** mark in this active, owned stream.
- `!relic reject last` removes only that selected pending mark. Approved and historical marks are unchanged; spent quota, serials and cooldowns are not refunded.
- `!relic block @login` blocks an immutable ID only when this command carries the matching structured mention in its signed provider fragments. Plaintext without that metadata stays unresolved and changes no data. This is a local application mark block, never a Twitch ban. Existing numeric `!relic block ID` remains unchanged.

“Last” excludes blocked authors and requires current consent/ownership, an open current stream, unpaused policy and an eligible same-room signed reviewer. Managed chat also checks the signed message time against stream start, consent, closure and the existing delivery window. Selection and mutation happen inside the same memory operation or Firestore transaction. Existing event/message receipts prevent an exact replay from selecting the next mark. Old signed deliveries remain subject to the original expiry checks; no claim is made about an external provider's unobserved redelivery behavior.

Pending-mark acknowledgement now includes the quiet `!relic pending` hint. It uses the same existing bounded reply path, ten-second command cooldown, actor/room receipt limits and room/global reply budgets. A moderation command can queue at most one such reply, never a batch or an automatic reminder job. Unauthorized, blocked, bot, copied, wrong-room, stale or inactive review requests receive no review reply. Outbound uncertainty remains at-most-once with no new retry.

## Signed mention resolution and deliberate limitations

The existing EventSub handler checks HMAC, subscription, room and message age before `parseChat`. The parser accepts only an exact two-fragment shape: literal `!relic block ` text followed by one mention. Concatenated fragment text must equal the command exactly. Mention text and `user_login` must case-fold to the command login; `user_id` must be a bounded immutable numeric ID. Null/malformed targets, extra target fields, URLs, conflicting/duplicate mentions and prototype-like names fail closed. `user_name` is ignored as display text. The field semantics follow the parent-reviewed [Twitch channel.chat.message reference](https://dev.twitch.tv/docs/eventsub/eventsub-reference/#channel-chat-message-event).

The parser keeps an ephemeral WeakMap proof bound to the exact parsed chat object, action, room, actor and message ID. Both signed-chat store paths pass that original object into lifecycle/reduceMark, including Firestore transaction retries. Object spread, JSON/structured clones, raw action fields and a different action cannot carry the proof. Trusted service/control paths that copy an actor do not acquire mention authority. No serialized magic marker is used or trusted.

Resolved named blocks retain the new command's current-stream/consent/closure/freshness and reviewer checks; they are not converted into the older numeric command before those checks. Inside the transaction they use the same 128-ID bound, content removal without quota/cooldown refund, share revocation and privacy cancellation rules. Only an actual block/removal effect triggers the existing privacy fences. Completed carried associations are purged through the existing origin-mark checks. Public reply text is static and contains no target login or ID. Replay receipts still prevent a repeated message from blocking a later mentioned ID.

No login is stored in a mark, block record, cache, roster or identity index. Existing blocked IDs and existing bounded receipts remain the only durable records of this operation. Plaintext clients, multiple-fragment variants outside this deliberately narrow shape, ambiguous metadata and unavailable provider mention metadata remain unsupported and receive the honest unresolved response. Public scores, display names, configured Keeper names and previous chats are never resolution authority. No provider lookup, permission, subscription or scope is added.
