# Daily observation — prepared, not installed

Operator review is required before installing any scheduler. Intended interval: **once daily2–15November2026 inclusive**, not before now, not a keepwarm. `ops/daily-check.mjs --once` refuses to operate outside that date window. Tests call its pure injected checker with synthetic transports; Codex never executes live observations.

Provide existing runtime configuration transiently: exact canonical `OVERLAY_ORIGIN`, `EVENTSUB_CALLBACK_URL`, client ID/secret, bot ID and the two Keeper IDs. Supply `TWITCH_BOT_ACCESS_TOKEN` from an **existing** bot grant through a parent-reviewed read-only adapter/transient environment. Do not put it in source, a persistent env example, logs or a new unreviewed secret object. The script does not load auth files, ADC, SDKs or Secret Manager, and does not decrypt/read the production grant itself. Parent must decide how an existing managed binding/VM identity supplies it without disclosure.

One run performs health GET, BOT token validation GET, an ephemeral APP client-credentials mint and bounded EventSub list GET(s). The mint is an explicit observational auth exception; it is not a user-grant refresh and is not persisted. Validate bot identity/client/base chat scopes. Check exactly five desired enabled webhook conditions per Keeper (online, offline, incoming raid, outgoing raid, chat with exact bot ID), version1 and exact canonical callback; tolerate only the documented unused empty opposite raid key. Three pages max, cursor bound/loop guard; incomplete results alert. It never creates/deletes subscriptions, bootstraps, mutates config or grants, raids, sends chat or invokes P7.

Output is only closed check names/status and process exit code. An expired401 means `reauth-or-explicit-refresh-required`: the **operator** handles that separately. No automatic refresh/save is falsely promised. Connect existing alert delivery only after reviewing its destination and permissions; no email/chat/scheduler installation is included. Calls are several observational requests/day, not “one request”; no free-cost guarantee. Keep the existing£1 budget and alerts.

Future operator checklist: review source and mocks → supply existing bindings privately → test one authorized read-only run → review structured output/no tokens → separately install date-bounded once-daily scheduler → stop/remove after15November. No command in this document applies a cloud policy or changes current traffic.

Scheduler tooling currently permits inspection/removal of the current job only; creation, update and wake are unavailable. This checker is prepared, not scheduled or auth-wired. No CLI/crontab workaround is authorized; an interactive operator installs the reviewed 2–15 November schedule after acceptance. Base three bot scopes suffice; P7 permissions are not required.
