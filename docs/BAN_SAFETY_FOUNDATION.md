# Ban-safety preparation foundation — local071, not activated

`src/ban-safety.js` is deliberately **not wired into OAuth, runtime, controls or the default five-subscription plan**. No new scopes, consent request, route, database write, dependency, scheduler or live provider call was added. Its constructor requires injected transport, grant-validation adapter and app-token provider; construction does no work. Explicit invocation is the only entry point. ## Contract and bounds

Configure two to four exact Keepers, a separate bot ID, application client ID and canonical HTTPS `/eventsub` callback. The injected `validateGrant(host)` must freshly validate a **user** grant with matching client and broadcaster ID, validation age at most60 seconds and unexpired token. Both `channel:moderate` and `moderation:read` are required; the documented broader `moderator:manage:banned_users` may satisfy the read permission instead, but **read-only moderation:read is recommended**. Bot/wrong-account/wrong-client/old/missing-scope proofs fail before subscription or bans HTTP. Adapter output is a trusted validation boundary, not permission inferred from a caller's claim or display name. No grant bodies/tokens are returned or logged.

`prepare(host)` defaults to snapshot/plan preparation without reconciling subscriptions. `prepare(host, { reconcileSubscriptions: true })` explicitly reconciles only exact `channel.ban` and `channel.unban` version1/broadcaster conditions using an injected **same-client app token**, never the user grant for webhook creation. Existing online/offline/raid/chat subscriptions remain untouched. Wrong callbacks/conditions or duplicate desired subscriptions fail closed; no DELETE, broad retarget, infinite retry or automatic migration. A409 permits bounded relist, never repeat-create. One bounded final list must show both enabled; pending/missing callbacks return failure, no prepared snapshot. Lists cap two100-item pages; all injected effects/timeouts are bounded to at most8 seconds each.

Ban reads use the validated own broadcaster **user** token at GET `/helix/moderation/banned?broadcaster_id=...&first=100`, at most two pages and128 total entries. Nonempty bounded cursors are URL-encoded; loops/incomplete pagination, duplicate users, invalid IDs/ISO dates, expired/malformed timeouts, capacity,401/403/429 and transport/timeouts fail closed. A complete snapshot returns only private `{userId,bannedAt,expiresAt}` records (null expiry for permanent bans), ignoring names/logins/reasons/moderator identities. Each date is validated independently. The private snapshot preserves provider order; no chronological API order is assumed. Parent review of the official reference found no newest-first guarantee. No partial snapshot appears on failure. Errors contain only closed stage and numeric/null HTTP status, never cursor/URL/raw response/error text.

Success says `prepared:true`, `snapshotComplete:true`, **`activated:false` and `globalReady:false`**. This is private preparation data, not a public projection, live policy activation or global ban readiness. Plan-only conditions explicitly say not-reconciled. The caller must keep snapshots private; there is no public HTTP endpoint. `parsePreparedUnban` is an unwired whitelist utility: only verified header time supplies ordering, since unban body has no trusted timestamp. It mutates nothing and cannot clear any block.
