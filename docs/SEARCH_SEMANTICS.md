This supersedes earlier “identity mapping absent” statements below only for **self-requested** history. `!relic mymarks` or `!relic mymarks @OwnLogin` requires original signed `chatter_user_id` and valid ASCII `chatter_user_login` (1–25 letters/digits/underscore, case-normalized). Optional argument must match that signed login; display names or entered names never prove identity. Missing/malformed login, bot and copied commands cannot mint a named grant. There is no public username index, arbitrary-other-viewer resolver, backfill, new scope or provider lookup.

Encrypted capability and bounded ephemeral grant bind channel, immutable actor ID, canonical login, nonce and ten-minute expiry. History joins retained mark.userId, **not mark text**, so “moon” can be found for its actual author even when the login differs. Shared page/API accepts only the bound name, optionally with @/ASCII case; wrong names/fields/pages fail closed and clear previous UI content. A link is deliberately shared in PUBLIC CHAT and anyone holding it can open; it is not a private login or proof of a link viewer. Initial capability read supplies the bound name, with no name in request URL/history/analytics/storage. The existing fragment-to-POST handling remains.

A new verified explicit self-request revokes older grants for that actor under another name, and older ephemeral same-name grants belonging to a different actor. Rename preserves immutable-ID history; a reused login never rekeys marks. No ordinary-chat identity index is written. Rate-rejected rename requests can revoke stale aliases but cannot refund cooldown or flush another request. Forget removes own alias/grant rows and content/associations; ban, policy, expiry and approval checks remain fresh, no durable alias collection. Delayed pages are ignored after input/change/clear/navigation; failed lookups hide prior content. Retained16-stop/160-mark bounds are not a lifetime-travel promise. Automatic exact-row reply guards and all known-ban/registration/unban limitations remain unchanged.

## Local signed self-sharing increment (not deployed)

`!relic mymarks` in your **original signed chat** is now an explicit opt-in to sharing approved history in PUBLIC CHAT. It proves the actor/channel for that request, not an entered account name or subsequent link viewer. Copied Shared Chat commands, bot messages, forged/expired tokens and cross-scope grants cannot authorize it. No new OAuth scope, account resolver or username index.

The signed original command atomically dedupes/rate-limits and queues a response, then awaits one bounded bot reply after durable acceptance. Its private stable hash binds configured channel, proven actor and original chat message ID. Exact-row claim is transactional before HTTP; a duplicate can claim only its own still-queued row, never another viewer's. Rate-rejected requests cannot drain other rows. Fresh grant/approval/forget/ban checks run before the bot call. Dispatching, sent and unknown outcomes never retry, including timeout or finalize failure. No owner click is required; **Send queued public mark-history link** remains recovery only for genuinely never-dispatched queued rows. No background/startup/automatic raid worker is added. The bot uses its existing channel grant and says anyone in chat can open the link; no text/body-supplied actor is trusted.

A fresh random nonce plus actor/channel/ten-minute expiry is encrypted/authenticated under a domain-separated derivation of the existing token-encryption key (no new secret/dependency). The URL fragment is never sent in a server request; the page immediately removes it from its history entry and keeps it only in transient memory/POST body. It is a **bearer link**, not private login: anyone who sees it can read its approved results until expiry/revocation. Browser/clipboard/chat copies cannot be recalled; if JavaScript does not run the fragment cannot be scrubbed. No analytics, query logging or durable browser storage is added.

Parent's networkless reproducer found that removing an old alias grant also removed its request-hash dispatch boundary. A replay under another valid EventSub delivery ID after the one-minute reply cooldown could send again and revoke a newer alias. This is a mocked regression, not a claim of production exploitation. Existing060363-test results precede this fix; parent final verification remains pending.

A separate private `shareReceipts` array now retains only a command hash and expiry for ten minutes, including rate-rejected commands. Duplicate lookup happens **before alias revocation**. At most128 receipts fit the existing128KiB mark document; capacity fails closed atomically and expired hashes are pruned lazily. Forget/rename/ban/lifecycle grant cleanup preserves these short-lived idempotency hashes, which contain no raw actor ID, login, nonce, token or mark content. They are not an identity grant or permanent username index; forgetting does not refund cooldowns/quotas. Fresh explicit message IDs can request new grants subject to existing limits.
