# What “Where has my mark been?” can truthfully find

Local polish audit: current main already implements the Should approved-text search and its exact heading. Canonical production hotfixd529 is fd05-based and does **not** include that Should; the older deployed UI can therefore lack the search entirely. This local increment does not deploy or alter production. The Atlas now gives the exact heading a visible navigation link/anchor and a name-as-mark-text example.

The search reads only surviving approved public mark **text** at completed stops. A name such as Alex is searchable only if `alex` was the submitted, approved mark text; results are shared text matches, not verified personal ownership. One-word/emoji normalization and literal substring matching remain unchanged. Up to16 retained stops ×160 entries are scanned in one bounded lineage read; each POST result page has at most20 matches. There is no all-time/unbounded promise or silent reconstruction of removed marks.

Private marks/history retain numeric user associations solely for moderation/erasure, not a public account-name journey index. No durable account-login-to-viewer-mark mapping or browser account-login lookup exists. The local signed-chat self-sharing flow below proves only the actor of that explicit request and makes a public bearer link, not a username index. Entering a name proves neither account identity nor ownership. Genuine account-name lookup would need separately designed authenticated viewer consent/opt-in and privacy-safe data/retention rules; it is not implemented here. No account resolver, OAuth scope, API subscription, public private-association projection or forgotten-link reconstruction is added.

Queries remain transient POST bodies, never URL/history/analytics/storage/logs. The static `#mark-history` navigation anchor contains no query. Only completed approved surviving text/runes are returned; pending/removed content and viewer IDs are excluded. Manual refresh/search reads fresh content. Failure/clear/navigation hides prior matches; downloaded old snapshots cannot be recalled.

Archive-path limit: each completed stop records approved marks from that source's actual current stream at the carry. The current carried overlay uses the latest received stop, not an inferred all-lineage carry-forward. Search reports only entries actually retained in those stops; it does not fill in every subsequent relic stop as a particular mark's travel, or reconstruct missing/forgotten associations. “Every stop” here can mean all matching retained public entries within the16-stop bound, not a verified complete personal lifetime route.

## Local signed self-sharing increment (not deployed)

`!relic mymarks` in your **original signed chat** is now an explicit opt-in to sharing approved history in PUBLIC CHAT. It proves the actor/channel for that request, not an entered account name or subsequent link viewer. Copied Shared Chat commands, bot messages, forged/expired tokens and cross-scope grants cannot authorize it. No new OAuth scope, account resolver or username index.

The command atomically dedupes/rate-limits and queues a response; it does not perform Helix calls in the webhook. The channel owner must click **Send queued public mark-history link** in their authenticated control, or explicitly invoke the trusted runtime reply service. One queued reply is processed per request. A marked dispatch is never automatically retried after a crash/ambiguous result. The bot uses its existing chat grant for that exact channel and says anyone in chat can open the link. No target account/actor can be supplied by request text/body.

A fresh random nonce plus actor/channel/ten-minute expiry is encrypted/authenticated under a domain-separated derivation of the existing token-encryption key (no new secret/dependency). The URL fragment is never sent in a server request; the page immediately removes it from its history entry and keeps it only in transient memory/POST body. It is a **bearer link**, not private login: anyone who sees it can read its approved results until expiry/revocation. Browser/clipboard/chat copies cannot be recalled; if JavaScript does not run the fragment cannot be scrubbed. No analytics, query logging or durable browser storage is added.

Fresh reads transactionally check an erasable private nonce grant and surviving approved source associations before projecting text/runes/stop/channel/time/ring fields only. Pending/current unapproved entries, user IDs, nonces and private associations are never returned.16 stops ×160 entries max,20 per page; actual recorded archive only, not every physical/lifetime carry. Self-forget removes own grants as well as content/associations; later reapproval cannot resurrect the old link. Policy/moderation/lifecycle changes conservatively revoke affected-channel share grants; expired links fail closed and clear rendered content. At most8 active grants/outbox rows per channel; one request per actor/minute, bounded128 hashed rate markers logically expire60s and prune lazily. Minimal rate records are retained on forget to prevent refund/spam; original mark quota/cooldown remains unchanged. Expired grant rows prune lazily on future requests; no cleanup job is promised.

The optional `node scripts/browser-smoke-handoff.js` uses only labelled memory/mock/synthetic-HMAC data and verifies public-link framing/fragment removal/forget/reload safety; no real login/provider calls.
